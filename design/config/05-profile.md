# プロファイル

実行単位。名前・説明・使用デバイス設定・変換グラフへの参照を一か所に束ねる。ブリッジはプロファイルをもとに動作する。

プロファイルには2つの位置づけがある。**ローカルプロファイル**は実機デバイス名・送信先（`connection`）を直接宣言する、利用者環境固有の非公開設定（本ページの基本形）。**配布用プロファイル**は環境依存の接続設定を持たず、配布を前提とする（[配布用プロファイル](#配布用プロファイル) 節）。

マッパーファイル（`transform` で指定）はグラフ定義のみを持ち、どのアダプターを使うかは持たない。アダプターファイルの解決はプロファイルが担い、`inputs[].id` / `outputs[].id` がマッパーのポート記法（`input.<id>.` / `output.<id>.`）と対応する。

```yaml
# profiles/my-setup.yaml

name: エレクトーン → VRChat
description: |                                         # 任意。ダッシュボードのカードに表示される説明文
  ELS-03 と VRChat を接続する基本セット。

inputs:
  - id: yamaha-els03                               # 省略時はアダプターファイルのベース名から自動生成
    adapter: adapters/yamaha-els03/yamaha-els03.yaml # 入力アダプターファイル
    connection:
      driver: midi
      device_name: "ELS-03 Series"                 # 実機と部分一致でバインドされる

transform: mappers/my-avatar.yaml                  # 変換グラフファイル

outputs:
  - id: vrchat-default                             # 省略時はアダプターファイルのベース名から自動生成
    adapter: adapters/vrchat-default/vrchat-default.yaml # 出力アダプターファイル
    connection:
      driver: osc
      host: 127.0.0.1
      port: 9000
      avatar_params: "C:/Users/.../OSC/.../Avatars/avtr_xxx.json"  # 任意（osc-vrchat アダプター種別定義の追加フィールド）
```

## セクション

| セクション | 必須 | 内容 |
|---|---|---|
| `name` | ❌ | 表示名 |
| `description` | ❌ | 説明文。ダッシュボードのプロファイルカードに表示される。複数行可 |
| `inputs` | ✅ | 入力アダプターと接続設定のリスト（1件以上） |
| `inputs[].id` | ❌ | 変換グラフから参照する識別子。省略時はアダプターファイルのベース名（拡張子除く）を自動使用 |
| `inputs[].adapter` | ✅ | 入力アダプターファイルのパス。ワークスペース内は `adapters/foo.yaml`、プラグイン由来は `@<plugin-name>/adapters/foo.yaml`（`<app-data-dir>/plugins/<plugin-name>/` に解決） |
| `inputs[].connection` | ✅ | 実デバイスとの接続設定。`driver` で内容が変わる |
| `transform` | ✅ | 使用する変換グラフファイルのパス |
| `outputs` | ✅ | 出力アダプターと接続設定のリスト（1件以上） |
| `outputs[].id` | ❌ | 変換グラフから参照する識別子。省略時はアダプターファイルのベース名（拡張子除く）を自動使用 |
| `outputs[].adapter` | ✅ | 出力アダプターファイルのパス。ワークスペース内は `adapters/foo.yaml`、プラグイン由来は `@<plugin-name>/adapters/foo.yaml`（`<app-data-dir>/plugins/<plugin-name>/` に解決） |
| `outputs[].connection` | ✅ | 実デバイスとの接続設定。`driver` で内容が変わる |

## connection の driver 別フィールド

`connection` のフィールドは、ドライバーの `connection_fields` 宣言から自動生成される。`connection_fields` の各エントリの `id` がそのまま YAML のキーになる。GUI はこの宣言をもとに接続設定フォームを生成し、ユーザーが入力した値をプロファイルの `connection` に保存する。

Driver SDK は任意キーに対する設定値を取得するための関数を提供する（`get_connection_field(key) -> value`）。ドライバーはこの関数を通じて接続設定値を取得する。

| driver | フィールド | 内容 |
|---|---|---|
| `midi` | `device_name` | OS が返すデバイス名（部分一致）。入出力共通 |
| `osc` | `host`, `port`, `listen_port` | 出力時: `host`・`port`（送信先）。入力時: `listen_port`（待ち受けポート）。双方向の場合は全て指定 |

アダプター種別定義（例: `osc-vrchat`）が `additional_fields` を宣言している場合、それらのフィールドも接続設定に追加される。`avatar_params` 等は osc-vrchat アダプター種別定義が宣言した追加フィールドであり、このテーブルには含まない。詳細 → [`../10-driver-plugin.md`](../10-driver-plugin.md)

## 接続のバリデーション

プロファイル読み込み時、`device_name` 等で指定された該当ポート・デバイスが OS 上に存在するかをデバイスごとに確認する。動的な ID 解決などの複雑な抽象化は持たず、プロファイルが実環境の接続情報を直接宣言するシンプルな方式をとる。

接続確認の結果はデバイスごとに独立して扱う。

| 状況 | 挙動 |
|---|---|
| 全デバイスが接続済み | ブリッジ起動可能 |
| 一部デバイスが未接続 | 未接続デバイスを灰色表示。ブリッジ起動不可（全デバイス接続が前提） |
| 全デバイスが未接続 | 同上 |

デバイスが接続されると自動検出し、全デバイスが揃った時点で実行ボタンが有効になる。

### 同時実行プロファイル間の競合

複数プロファイルを同時に実行する場合（[実行の制約](#実行の制約)）、エンドポイントの競合をプロファイル間でも確認する。競合の**検出**はアプリが行い、競合時の**挙動はドライバーが宣言する**（入力側で物理入力の同定をドライバーが `physical_input_identity` で宣言するのと対称）。

| エンドポイント種別 | 例 | 競合の判定と挙動 |
|---|---|---|
| 排他的入力 | OSC 受信ポート（`listen_port`）・MIDI 入力デバイス（`device_name`） | ドライバーの `physical_input_identity` で同定。トランスポート上の排他バインドのため共有不可——実行中プロファイルが占有する入力を要求する後発プロファイルは起動不可 |
| 出力先 | 出力アダプターが解決する送信先（OSC アドレス＋宛先 host:port 等） | 実行中プロファイルと**同じ送信先**へ書き込む後発を検出（**出力バッティング**）。挙動は出力ドライバーの `output_conflict` 宣言に従う——`block` なら後発を起動不可、`warn` なら起動は許し警告のみ（OSC は last-write-wins のため既定 `warn`）。同じ出力デバイスでも、解決後のアドレスが重ならなければ競合しない |

出力先は**解決後の送信先**で判定する。変換グラフの出力ブロックのポート（Signal 指定子）はプロファイルごとのローカルな名前で、プロファイル間で直接は比較できない——同じ `/avatar/parameters/UpperExpression` を別名ポートや別 `device_id` から書くこともあれば、同名ポートが別アドレスに解決されることもある。また送信トランスポート（同じ :9000 ソケット）で見ると全アドレスが同一経路に潰れて区別できない。そこで、駆動しているポートを出力アダプターの `binding.output` で実際の OSC アドレス（送信先 host:port 付き）へ解決し、その**解決後の送信先**が重なるかでアプリが競合を検出する（算出はプロファイルの `outputs`・出力アダプター・変換グラフの宣言から静的に行う。動的なアドレス解決は持たない）。検出した競合をどう扱うか（block / warn）は、その送信先を担う出力ドライバーの `output_conflict`（→ [`../10-driver-plugin.md`](../10-driver-plugin.md)）が決める。これにより、アセット同梱プロファイル（アセット用パラメーターを書く）とアバター側プロファイル（アバターのパラメーターを書く）は別アドレスなので競合せず、同じパラメーターを取り合う場合のみドライバー方針に従って止める／警告する。

**既知の制約**：排他的入力は出力と違いポート単位に分割できない（UDP の排他バインドはトランスポートの制約）。したがって VRChat からの OSC 受信（例: `listen_port: 9001`）を `inputs` に持てるのは、同時実行中の**1プロファイルだけ**。アセット側＋アバター側の並走は、OSC 受信を使うのが片方だけ（典型: アセット側は MIDI 入力→OSC 送信のみ、アバター側が OSC 受信を持つ）の構成で成立する。両方が VRChat からの受信を必要とする構成は現時点で非対応（受信を1か所で受けて各ブリッジへ配る共有レシーバーは将来拡張 → [`../05-future.md`](../05-future.md)）。

## 配布用プロファイル

配布を前提とするプロファイル。エレクトーンのアバターアセット（モデル・ギミック・プロファイルを同梱）のように、作者が用意したプロファイルを他の利用者へ渡すための形態。

ローカルプロファイルとの違いは **`connection` を持たない**こと。`device_name` や `avatar_params`・絶対パスといった環境依存の値は配布物に含めず、利用者が取り込み後に**アクティベート**（実機デバイス・送信先の割り当て）して初めて実行可能になる。

### プロファイルパッケージ

配布用プロファイル単体ではなく、それが依存するアダプター・変換グラフを1単位にまとめた **プロファイルパッケージ** として配布する。これにより取り込み側に依存物を別途用意させずに済む。

```text
<package>/
  .midori/package.yaml     # マニフェスト（パッケージ名・バージョン・収録プロファイル・同梱依存・依存プラグイン・依存ドライバー）
  profiles/<name>.yaml     # 配布用プロファイル（connection なし）
  adapters/...             # 同梱する（ワークスペース内の）依存アダプター
  mappers/...              # 同梱する（ワークスペース内の）依存変換グラフ
```

パッケージが**同梱する**のはワークスペース内のアダプター・変換グラフ（いずれも宣言的 YAML）に限る。**プラグイン由来**のアダプター（`@<plugin-name>/` 参照）は同梱せず、マニフェストに依存プラグインとして記録する（取り込み側がプラグインを別途インストールする）。**ドライバー本体（バイナリ）も含まない**——パッケージが参照する `driver` は利用者がプラグインとして別途インストールする。これによりパッケージ取り込みはプラグインのようなコード実行を伴わず、サンドボックス対象外でよい（プラグインのセキュリティ要件 → [`../11-security/01-driver-sandbox.md`](../11-security/01-driver-sandbox.md)）。

エレクトーンの VRC アセットには、このパッケージを同梱する。利用者は VRC アセットを導入したのち、同梱パッケージをアプリに取り込む。

### 公開用に出力（エクスポート）

ローカルプロファイルを配布用プロファイルパッケージとして書き出す、作者側の操作。プロファイル詳細画面から実行する（[→ `../07-ui-ux/07-profile.md`](../07-ui-ux/07-profile.md)）。取り込み（[取り込みとアクティベート](#取り込みとアクティベート)）の逆操作にあたる。

1. **接続設定の除去**：`connection`（`device_name`・`avatar_params` の具体値・絶対パス等の環境依存値）を取り除き、配布用プロファイル（connection なし）にする。マッパーが使う論理 ID（`inputs[].id` / `outputs[].id`）は環境非依存なので残す。
2. **依存物の収集**：プロファイルが参照するアダプター・変換グラフのうち、ワークスペース内のものをパッケージへ同梱する。プラグイン由来のもの（`@<plugin-name>/` 参照）は同梱せず、マニフェストに依存プラグインとして記録する。参照する `driver` も id でマニフェストに記録する（本体は同梱しない）。
3. **マニフェスト生成**：`.midori/package.yaml` にパッケージ名・バージョン・収録プロファイル・同梱依存・依存プラグイン・依存ドライバーを書き出す。
4. **出力**：以上を1単位の配布物として書き出す。作者はこれを VRC アセット等へ同梱する。

### 取り込みとアクティベート

1. **取り込み**：パッケージをアプリで取り込むと、収録された配布用プロファイル・同梱の依存アダプター・変換グラフが現在のワークスペースへ統合される。既存ファイルとの id 衝突はパッケージ名で名前空間化して回避する。マニフェストの依存プラグイン・依存ドライバーが未インストールなら、導入を促す。
2. **アクティベート**：取り込んだ配布用プロファイルを初めて実行する際、アプリが実機デバイス（`device_name`）と送信先（`avatar_params` 等）の割り当てを利用者に求める。割り当てた `connection` はワークスペース内のプロファイルへ保存され、以降はローカルプロファイルと同様に動作する。

アバター側に既存のプロファイルがある場合でも、アセット同梱の配布用プロファイルは別プロファイルとして取り込まれ、[同時実行](#実行の制約)により両者を並走させて管理できる（VRChat からの OSC 受信を持てるのは片方だけ → [同時実行プロファイル間の競合](#同時実行プロファイル間の競合)の既知の制約）。

## 実行の制約

複数のプロファイルを**同時に実行できる**。各プロファイルは独立したブリッジプロセスとして起動し、GUI が複数のブリッジプロセスを管理する。ブリッジ↔ドライバー間の共有メモリリングは常に「1ドライバー ↔ 1ブリッジ」の1:1を保つため、プロファイル（=プロセス）を増やしても既存リングの読み書き手は増えず、同時実行数に依存してデータ競合リスクが上がることはない（リングの不変条件 → [`../17-driver-comm/01-inline-ring.md`](../17-driver-comm/01-inline-ring.md)「単一 Driver プロセス前提」）。

同時実行できるかはエンドポイントの競合で決まる。排他的入力（同一 OSC 受信ポート・同一 MIDI 入力デバイス）の共有は、トランスポートの排他バインドのため必ず後発プロファイルを起動不可にする。同じ送信先への二重書き込み（出力バッティング）は、出力ドライバーの `output_conflict` 宣言に従って起動不可（`block`）か警告のみ（`warn`）かが決まる。トランスポート上は出力の排他バインドが不要なため複数プロファイルからの送信自体は可能（プロセス分離が成立する理由）で、競合をどう扱うかはドライバーに委ねる（[同時実行プロファイル間の競合](#同時実行プロファイル間の競合)）。
